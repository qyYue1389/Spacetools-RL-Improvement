## 2026-09-12 追加:五个环境的 Python 版本不一致(重要)

  spacetools-rl                3.11.16   ← Ray 集群头节点用这个
  spacetools-tool-vlm          3.11.0    ← 与头节点不一致
  spacetools-tool-roborefer    3.11.16
  spacetools-tool-bbox         3.11.0    ← 与头节点不一致
  spacetools-tool-graspgen     3.11.16

Ray 的 check_version_info 默认按完整版本串比较(patch 档),3.11.0 != 3.11.16
会抛 RuntimeError,那两个环境里的 actor 全部入不了 Ray 集群。

影响范围:
  eval 的四个空间推理 key(robospatial/reflocation/refplacement/refunseen)
      只用 roborefer + 偶尔 depth/vision_ops,受影响有限,但 8 个 actor 静默缺席
  依赖全套工具的 key(blinkdepth / cvb3ddepth / boppose / bopgrasp)会受影响
  RL 阶段有 23 个 actor 在这两个环境里,全部起不来

缓解:bash POSTRESTORE.sh —— 用 Ray 自带的 minor 档放宽该检查。
      两侧 bytecode magic(3495)与 pickle 协议(4)相同,code object 与 pickle
      互通,这正是 minor 档的设计场景;该改动不改变任何数值。

根治:重建环境包时把五个环境的 Python 统一到 3.11.16。做到之后
      POSTRESTORE.sh 的第 ① 项会自动跳过,可以删掉这个脚本。
      注意:本机上 conda 升级 Python 被 Anaconda 频道的 Terms of Service
      拦住(CondaToSNonInteractiveError),而且重新求解有动到
      numpy 1.26.4 / transformers 4.53.2 等钉死版本的风险,所以没有就地升级。

## 2026-09-12 追加:GPU 预算(实测)

这套七工具配置的 Ray 逻辑预留是 2.3 张卡(run_eval.sh:132-142)。
策略模型(verl,trainer.n_gpus_per_node)要的是**整张卡**,不能是分数。

4 卡机器上必须设 NUM_GPUS=4 EVAL_GPUS=1(默认值是 8 / 4,EVAL_GPUS=4 会让
2.3+4=6.3 > 4.0,Ray 不报错、actor 无限排队)。即便如此仍然偏紧:需要 Ray
恰好把 2.3 压成 1.0/1.0/0.3 留一张整卡出来,否则 verl 的 WorkerDict 拿不到
GPU,会在 fsdp_workers.py:158 抛
    ValueError: Duplicate device type cpu in backend string: nccl
      (cpu:gloo,cpu:nccl —— verl/utils/device.py 的 is_cuda_available 是
       模块导入时求值,无可见 GPU 时 get_device_name() 永久返回 cpu)

实测单卡峰值(4× A6000,全工具存活):
  Molmo(vlm)      30.2 GiB   ← fp32,vlm.py:116 的 torch_dtype="auto" 吃掉了
                                 配置里的 dtype: float16
  与 depth 同卡时  该卡合计 46.3 GiB / 48 GiB   ← 40 GB 的卡装不下
  roborefer        18.2 GiB
  策略侧           41.6 GiB(verl FSDP 15310 MiB + sglang scheduler 27292 MiB)

RL 阶段的 actor 数量远大于 eval(roborefer 6、sam2/depth/bbox/graspgen 各 5、
vision_ops 8),预留约 7 张卡以上,4 卡结构上装不下,必须重新算。
